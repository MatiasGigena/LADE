# Wire protocol v1 (bundle 0.2.0)

Concrete application protocol for the first release. It supersedes the IMP-001 fixture command set; its framing, bounds, duplicate-operation and admission safety properties remain in force. Admission is documented in [service.md](service.md#admission-transport).

## Envelope, limits, framing

`{"protocol":1,"bundle":"0.2.0","body":{"kind":…}}` for both contracts. Decoding is always: bounded JSON parse (1 MiB body, depth 32, 16,384 values, 1,024 members, 256 KiB per string, duplicate keys/lone surrogates/non-integer numbers reject) → exact protocol **and** bundle (`version_mismatch` first) → closed schema → typed DTO. Unknown fields, missing required fields, `null` for an optional field and wrong JSON types reject without coercion. Client framing is a u32 big-endian length + body; worker framing is body + LF (JSONL). A framing error poisons the link; the decoders retain one body and deliver one frame at a time. Encoding serializes inside the 1 MiB cap and re-decodes the bytes before they leave, so a sender can never emit what the peer must reject (callers truncate long text with `truncate_utf8`/`truncate_chars` or `Rejection::new`).

Budget note: one frame holds at most 16,384 JSON values. Lists (objectives, files, hunks, diff lines, activity items) carry schema `maxItems`, and services must page or set `truncated` before reaching the value budget; `encode` returning `frame_size`/`limit_reached` is a service bug, not a peer error.

### Chunk ownership and queue budgets

Chunk transfers use an opaque UUID, connection-bound owner scope and execution generation, a declared decimal
total length and lowercase SHA-256 digest. Data is canonical lowercase hex, at most 64 KiB decoded per chunk.
Indices must be consecutive from zero, data non-empty, and the total and digest exact on completion; no data is
accepted after completion or cancellation. At most two transfers and 8 MiB per transfer per link (16 MiB reassembly)
are allowed within component memory budgets. Start validates before allocation; data grows incrementally. An
invalid transfer clears the reassembler; cancellation, disconnect or authority loss frees incomplete content.
Completed bytes transfer to the caller under its own bounded queue. Transport lifecycle must cancel abandoned
transfers. These are staging bounds, not pi logical-content limits; larger content uses service-owned artifacts
and paging, never an automatic unbounded disk spill.

Outbound budgets are 8 MiB/256 frames per direction and 32 MiB service-wide; replay is bounded to 16 MiB/10,000
events. Reserve 1 MiB and 16 slots per outbound link for cancellation/control, and 4 MiB service-wide. Producers
obtain capacity before serialization. Overflow causes explicit backpressure, resync or failure, not semantic loss;
control cannot preempt bytes already in an ordered frame. See [performance budgets](../planning/performance-budgets.md)
and the [service implementation](service.md) for targets and enforcement.

### Schema subset

`$ref`, `oneOf` (exactly one match), `const`, `enum`, `type: object` (`additionalProperties: false`, `required` ⊆ `properties`; non-required = optional, omitted when absent), `type: array` (`items`, mandatory `maxItems`, optional `minItems`), `type: string` (optional `format`, `minLength`, `maxLength` counted in Unicode code points), `type: boolean`. There are no JSON numbers besides `protocol`; counters are decimal strings. The generator asserts the subset; both validators fail closed on anything else.

### Formats

| format | rule |
| --- | --- |
| `uuid-v4` | canonical lowercase UUID, version 4, RFC variant |
| `u64` | canonical unsigned 64-bit decimal (no sign, no leading zero except `0`) |
| `page-limit` / `read-limit` | canonical decimal `1..=200` / `1..=262144` |
| `sha256`, `capability` | 64 lowercase hex |
| `git-sha1` | 40 lowercase hex (`GitId` binds `sha1`→40, `sha256`→64) |
| `chunk-hex` | non-empty even-length lowercase hex, ≤ 64 KiB decoded |
| `timestamp` | RFC 3339 UTC, single canonical form `YYYY-MM-DDTHH:MM:SS.mmmZ`; years 1970–9999, real calendar dates, no leap seconds |
| `path-b64` | canonical padded RFC 4648 base64 (standard alphabet, zero pad bits) of 1..=4096 raw bytes |

Paths are `{b64, display}`: `b64` is the authority (lossless bytes, `WirePath` ⇄ `Vec<u8>`/`OsString`); `display` (≤ 4096 code points) is a lossy label and never authority.

## Client ↔ service

Bodies (`ClientBody`): `hello` (both; version declaration, never authentication), `auth {capability}` (C→S), `welcome {service_epoch, lease_id}` (S→C), `request`, `reply`, `event` (S→C), and the retained `chunk.start/data/end/cancel`.

`request {request_id, operation_id?, name, payload}`: the schema has one variant per name, so the payload is typed by name and **`operation_id` is required for mutating names and forbidden for queries**. `reply {request_id, name?, result}` with `result` = `{status:"ok", data}` or `{status:"rejected", code, action, detail ≤ 512 code points}`. The reply echoes the request `name` so `data` is schema-checked per name; `name` is omitted only for the rejection of a request whose name could not be read. `event {service_epoch, sequence, name, payload}`; a sequence gap means re-query `snapshot`.

### Contained terminal and lifetime (IMP-012, additive)

The `terminal.*` names are *interaction* with a service-owned PTY: like queries they carry no `operation_id`
(the schema forbids it), are never journaled, replayed or resent after a reconnect, and create no durable state; a
terminal is bound to the controlling lease and dies with it. Sizes are decimal strings; the service accepts
1..=500 columns and 1..=200 rows. `terminal.output.seq` starts at 1 and increases by one per event of a terminal; a
gap (for example after a resync) and a non-zero `dropped_bytes` (output discarded by the service's bounded buffer)
are shown to the developer as an explicit marker, never silently joined. Output is UTF-8 text decoded by the service
(invalid bytes replaced, NUL removed); input is the UTF-8 the client's VT encoder produces (no NUL).
`service.stop` is an ordinary journaled command: the reply is sent, then the service stops its workers and
terminals and exits; a client that sent it neither reconnects nor starts a new service.

### Repository inspection additions (IMP-004/009, additive)

All optional fields, so older peers' frames stay valid and an older client simply ignores what it does not know:

- `ChangedFile.filtered` (`true` only): the path's `filter` attribute names a filter driver (Git LFS,
  `clean`/`smudge`); LADE never runs filters, so raw working-tree bytes are compared — unsupported content.
- `ChangeList.notices` (≤ 64 `ContentNotice {kind: nested_repository|filtered_content, message ≤ 512, path?}`):
  a nested repository without a commit left out of a working capture (one per path), and one repository-level
  notice when any listed file is filtered.
- `SearchResult.column` (1-based byte column of the first match in its line) and `byte_end`; `byte_start` (already
  in the schema, previously unset) is now filled for content results. `[byte_start, byte_end)` addresses the raw
  file bytes `file.read` retains, so it can be used directly as a feedback reference range; both are omitted when
  the file exceeds 16 MiB, the per-search 64 MiB offset budget is spent, or the match cannot be confirmed.
- `FileContent.chunked` (`true` only): the file exceeds the 64 MiB whole-file bound (hard upper bound 1 GiB) and is
  served in chunks of at most `limit` (≤ 256 KiB) through the existing `offset`/`limit` of `FileReadQuery`. The
  `artifact_digest` still names the whole file; encoding is decided by a NUL in the first 8,000 bytes; a text chunk
  is cut back to a character boundary, an offset inside a character is `invalid_request`, and a chunk that is not
  UTF-8 is `unsupported_content` (no gaps in the text).
- The `ActionName` `terminal.open`: the only interaction in `available_actions`, so the client enables "Open
  terminal" from the service's scope (worktree exists, lifecycle admits a terminal, sandbox works) instead of
  guessing; an enabled entry may carry a note (read-only while frozen). Its reason equals the `terminal.open`
  refusal detail.
- `available_actions` reasons, `InputSummary.blocked_reason` and rejection `detail`s are short developer-facing
  sentences ending with a period; the client shows them as they are and keeps `code` for technical details only.
- `ObjectiveDetail.history_deleted` (`true` only) and the `ActionName` `objective.delete_history`: the deliberate
  deletion of a cleaned-up Objective's retention refs and branch. `confirm_history_loss` must be `true` (otherwise
  `invalid_request`); it is never sent by the service or client on its own.

Every `DiffLine` includes the required boolean `no_newline`, preserving Git's missing-final-newline
marker. `text` excludes the line's LF and preserves its CR bytes. Thus `text: "line\r"` with
`no_newline: false` represents a CRLF line, while the same text with `no_newline: true` ends in a bare
CR. The inspection surface hides the CR of a CRLF ending and exposes a bare CR without changing the
raw bytes used by feedback references.

### Error semantics

`ErrorCode` keeps the IMP-001 codes and adds `not_found`, `invalid_request`, `conflict`, `execution_unavailable`; `SafeAction` is unchanged. A frame that parses as bounded JSON with exact versions and whose body is a `request` with a valid `request_id`, but fails the schema (unknown name, invalid payload, wrong `operation_id` presence), is answered with an unnamed or named `invalid_request` rejection and the link stays open — `decode_client_frame` returns that `request_id` for exactly this case. Every other decode failure (framing, JSON, version, non-request schema failure) closes the link. `auth` failure closes the link without a reply. `Rejection {status, code, action, detail, stale_drafts?}`: `detail` is human-readable prose (or empty when the code says it all) and never carries source, prompt or secret content, codes or identifier lists; a `stale_reference` from a feedback batch names the drafts whose anchors no longer match in `stale_drafts` (1..=256 ids), which clients read instead of parsing `detail`.

### Draft and input pages

`DraftsListQuery {objective_id, limit, after?: DraftCursor}` reads drafts in ascending
`(created_at, draft_id)` order. `DraftCursor {created_at: Timestamp, draft_id: Id}` uses the draft's
immutable creation time and UUID; comparison is exclusive, so deleting the cursor's draft does not
invalidate traversal. `InputsListQuery {objective_id, limit, after?: Counter}` reads inputs in ascending
durable acceptance-sequence order; the sequence is the cursor, including when acceptance timestamps tie.
Omit `after` for the first page. `limit` uses `PageLimit` (`1..=200`).

`DraftList {drafts, next_after?: DraftCursor}` and `InputList {inputs, next_after?: Counter}` contain at
most `limit` full records and must fit the encoded frame and JSON-value budgets. The service can return
fewer records to meet the byte bound. When records remain, `next_after` identifies the last emitted
record and advances strictly beyond the request cursor; a continuation page is never empty. Omission
of `next_after` completes the traversal. No records are silently skipped to fit a page, and paging
imposes no limit on the number of durable drafts or inputs. An existing record that cannot fit even
alone produces an explicit rejection while its durable content remains intact.

The desktop accumulates a complete traversal before publishing the authoritative list or reconciling
absent drafts. It applies events, command outcomes and confirmed draft deletions in connection order
while loading, and ignores replies from a replaced traversal. Only the final successful page releases
saves waiting for draft reconciliation. A failed traversal or disconnect preserves the current list
and local text; a subsequent traversal starts with `after` omitted.

Before committing a draft save, the service checks that the resulting record can be sent in its save
reply, a one-record page with a continuation cursor, its `draft.changed` event, and the recovered
`operation.get` outcome. An unrepresentable save is rejected before changing durable content.

### Duplicate operations

`RequestFrame::canonical_digest()` hashes the validated canonical content excluding `request_id` (`operation_id`, `name`, `payload`; object keys sorted, arrays in order, exact strings). For a mutating request: same `operation_id` and digest → return the original recorded reply (never re-execute, never the new claimed outcome); same `operation_id`, different digest → `duplicate_conflict`; a reused `request_id` with different content or operation → `duplicate_conflict`. After disconnect/restart the client queries `operation.get` rather than blindly resending. The test-only reference `RequestHistory` in `crates/lade-protocol/tests/support/history.rs` (256 identities, `limit_reached` instead of eviction) checks the contract fixtures against the rule; the service applies it through its durable operation journal, and remembers the digests of the last 4096 request ids per client connection to refuse a reused `request_id`.

## Service ↔ worker (`worker-schema.json`, JSONL)

Service → worker: `worker.start {objective_id, session_dir, cwd, model, resume, system_note, thinking?, resources?: WorkerResources {profile_dir, extensions: [{name, path, sha256}]}, session_file?}`, `input.deliver {input_id, mode, text (non-empty)}`, `session.abort {}` (clears queued steer/follow-up, then aborts), `session.command {command_id, command: SessionCommand}` (`op` = `tree`, `navigate {entry_id}`, `fork {entry_id, position}`, `import {path}`, `export {path}`, `compact {instructions?}`, `reload {resources}`, `configure {model, thinking}`), `ui.respond {ui_id, generation, answer}`, `worker.shutdown {}`. Worker → service: `worker.ready {pi_session_id (pi's own id, a bounded string, not necessarily UUIDv4), session_file (may not exist yet)}`, `input.received {input_id}`, `activity.item {item_id, role, title ≤ 1024, text, tool_name?, is_error, truncated}`, `activity.delta {item_id, append_text}`, `turn.state {running|idle}`, `worker.error {code: WorkerErrorCode, message ≤ 512}`, `session.result {command_id, ok, message ≤ 512, entries?, leaf_id?, truncated?}`, `session.changed {generation, reason, model, thinking, pi_session_id, session_file, leaf_id?}`, `resources.loaded {generation, resources: LoadedResource[]}`, `ui.request {ui_id, generation, prompt}`, `ui.closed {ui_id, reason}`. The worker validates against a package-local generated copy (`packages/pi-worker/src/worker/worker-schema.json`), because the sandbox binds only the worker package. Sandbox paths are plain strings of 1..=4096 code points chosen by the service.

Semantics: an `activity.item` whose `item_id` was already sent is an upsert — the final authoritative text replaces the streamed one (deltas apply to the latest text of that item). Text over 192 KiB in one item is truncated by the worker with `truncated: true` and the full byte length noted in `title`. The service binds each worker link to one Objective at launch, rejects bodies of the wrong direction (`WorkerBody::is_from_worker`, TS `isServiceToWorker`/`isWorkerToService`) and treats any worker decode failure as a protocol violation that closes the worker link. Worker reports are never approval, verification or durable acceptance.
