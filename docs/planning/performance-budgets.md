# GTK4 performance targets and acceptance handoff

**Accepted provisional engineering targets and evidence handoff—not measured production guarantees.** The maintainer explicitly approved the proposal and handoff in [#13's resolution](https://github.com/MatiasGigena/LADE/issues/13#issuecomment-5698708894), based on the draft at local commit `ae606b3`. [GTK4 selection](client-architecture.md) and the approved interaction remain unchanged. Approval resolves the planning decision by accepting targets and assigning implementation/release evidence—not by pretending the miniature already passes them. Production implementation still requires separate authorization after #14.

## Evidence versus allocation

The [published comparison report](https://github.com/MatiasGigena/LADE/issues/13#issuecomment-5698278583) measured the native C miniature at **76.3 MiB median settled PSS**, **10.9% stream/typing CPU** and **2.8% settled CPU** (one logical core), **0.327s median launch-to-ready**, and **32.1–51.1ms per-run input scheduling-proxy p95**. Those are short-run observations on Mint/Cinnamon/X11, not real presentation, Rust-client costs, rich diff rendering, workers or service load.

The client targets below leave roughly twice the observed settled memory and stream CPU for the real presentation layer; this is an engineering allocation, not evidence that the allowance is sufficient. The idle CPU target deliberately requires improvement over the miniature. Service/worker values are **unmeasured provisional allocations**, to be challenged at the first integrated slice. No historical RPC idle measurement is substituted for the selected SDK runtime. Latency targets express the desired product floor, not a statistical inference from frame callbacks.

## Reference workload and accounting

- Supported reference: Mint 22.3 / Cinnamon / X11 / x86_64, the recorded Ryzen 7 5825U host, hardware acceleration and 60Hz display. Record actual RAM, kernel, renderer, versions and background load each time. Lower-end hardware is not certified by these targets.
- **Idle:** 32 Objective records, no executing workers or jobs, full file open, 30s settling followed by 60s measurement. Also measure an idle already-open worker separately without changing the approved lazy worker lifecycle.
- **Nominal:** the same 20,000-line / 1,280,000-byte UTF-8 file and 4,000-line / 184,000-byte signed diff, switching/selection/feedback during 20 UI updates/sec. Extend in implementation to actual chosen text/diff controls, 10,000 transcript entries totaling 10 MiB, and deterministic SDK streams with **one, then four active Agent Sessions** in separate Objectives. Four is a validation point, not a product concurrency cap. Pin the input/event trace so repeated runs do the same work.
- **Stress, separate from nominal latency:** a 20 MiB file, 100,000-line diff, one contextual terminal producing 1 MiB/s for 30s, event bursts and a disconnected/slow client. Require bounded memory, honest paging/partial-view labels, input/control availability and safe resync; do not promise immediate full rendering. Full-file access remains available through bounded views; no apparently complete truncation.
- Sum **PSS** across each owned process group; CPU is percent of **one logical core** (100% = one busy core). Client helpers count with client; Rust/Git/search/gateway helpers count with service; Node/SDK runtime counts with its worker. Report tool/terminal job descendants separately **and in an all-owned total**. Never hide a build's memory by reporting only the UI.
- PSS excludes GPU allocations and differs from cgroup memory. Record cgroup `memory.current`/peak/events and CPU accounting separately, including short-lived descendants; no conversion of PSS targets into `MemoryMax` is implied. Arbitrary builds, model execution and provider latency are not covered by the runtime-only envelopes below.

## Accepted provisional numerical targets

Memory targets apply to every run: median settled PSS for idle; maximum sampled PSS for nominal load. CPU targets use interval-weighted means over the stated window. Every allocation includes the component's bounded caches/queues; it is not permission to add those on top.

| Boundary | Accepted target | Evidence / consequence |
| --- | --- | --- |
| GTK4 client PSS | **≤150 MiB idle; ≤250 MiB nominal peak** | Anchored to ~76 MiB miniature only; rich controls/client binding unmeasured. |
| Rust service group PSS | **≤64 MiB idle; ≤128 MiB nominal peak** | Allocation only. Measure storage, Git/search and gateway overhead in the integrated slice. |
| Per SDK worker PSS | **≤128 MiB idle; ≤256 MiB nominal peak** | Allocation only, for the specified short-context trace—not an arbitrary extension/context/tool guarantee. Preserve pi semantics; never meet it by removing required providers/tools or silently shortening context. |
| Runtime-only aggregate | **≤214 MiB with no worker idle; ≤634 MiB with one worker nominal; ≤1,402 MiB with four** | Sums of allocations, **not measured totals**. Job descendants and GPU remain separately reported costs. Idle service with window closed: service allocation only. |
| Idle CPU | Client **≤1%**, service **≤0.5%**, each idle worker **≤0.5%** | Mean over 60s; cursor/focus visible in client. The miniature's ~2.8% does not meet this aspirational client target. No decorative continuous redraw/polling as the default. |
| Nominal presentation CPU | Client **≤20%**, service **≤20%** | SDK model/event processing and jobs reported separately. Worker CPU is workload-dependent; no arbitrary universal agent-compute CPU cap is selected here. |
| Local input and navigation | **p95 ≤100ms; no sample >250ms** | Input event → confirmed corresponding visible presentation, while streaming. Typing/selection and already-loaded Objective/view navigation; not provider completion. Frame callbacks are diagnostic proxies only. |
| Open reference file/diff | **p95 ≤500ms** to first usable, version-labelled viewport | Nominal file/diff sizes above; local capture/read/render included, not just widget population. Search/large work shows progress and cancellation rather than blocking the UI; no repository-wide search completion promise is inferred. |
| Launch | **p95 ≤2s** to usable presented workbench | OS-cache-warm, service initially stopped, existing local Workspace metadata; no worker/model startup dependency. Installed first-run/cold-cache behavior measured separately, not mislabeled warm. |
| Draft-save scheduling | Request after **300ms** quiet, and at least every **2s** during continued typing; durable acknowledgement **≤1s after request** under healthy local storage | Target unacknowledged edit age ≤3s under those conditions, not a crash-loss guarantee. Saved requires the exact durable revision acknowledgement. Overdue/failed/disconnected remains visibly unsaved; #14 subsequently accepted safe-close/loss-confirmation and restore-unsent/no-auto-submit policy; concrete durability remains unverified. |

These are acceptance targets, **not automatic kill thresholds**. A breach triggers investigation and a retained failure; it never authorizes deleting history, discarding drafts, bypassing containment, silently trimming SDK context or relabeling failed work as successful. If a target conflicts with required behavior, present evidence and obtain an explicit adjustment rather than silently raising it.

## Accepted initial transient bounds and overflow behavior

These are design allocations, not measured transport guarantees. Concrete schemas and adversarial allocation tests precede implementation of the boundary.

| Resource | Initial bound | Required behavior at the boundary |
| --- | --- | --- |
| LADE-owned client and worker transport frames | **1 MiB encoded UTF-8 body per frame** | Check length/bounded JSONL accumulation before unbounded allocation; bound decoded structures too. Page/chunk larger logical content or reference an owned artifact. This is **not** a 1 MiB pi input/tool-result limit: preserve logical payloads, ordering, identities and compatibility. Oversized/malformed frames are explicit protocol errors, never partial acceptance. |
| Pending outbound frames | **8 MiB or 256 frames per link direction**, whichever first; **32 MiB service-wide** | Bound both serialized and decoded staging inside memory allocations. Reserve capacity for control/cancellation. Coalesce only replaceable display projections; never silently drop commands, durable results, feedback or authority transitions. Disconnect/resync a slow client rather than indefinitely buffering it. Worker pressure must have a bounded, tested drain/spool or explicit failure path, not deadlock tools or consume unlimited disk. |
| In-memory client replay cache in Rust | **16 MiB or 10,000 events**, whichever first | Expired cursor requires authoritative snapshot plus paged durable history, not replay guessing. Evicting transient cache never deletes accepted history, pi sessions, review artifacts or drafts. |
| Routine streaming presentation | At most **20 updates/sec per visible stream**, with aggregate work subject to the CPU/latency targets | Batch repaint work, not pi semantics or durable event capture. Prompt/control/error handling is not forced to wait for the repaint cadence. Screen-reader output follows #17's grouped attention policy, not token narration. |

Hard cgroup limits for arbitrary jobs, persisted diagnostics retention, capture/artifact quotas and disk-exhaustion behavior are **not numerically settled by these PSS/queue allocations**. #14 has accepted their [policy and pre-implementation gate ownership](implementation-readiness.md#accepted-14-diagnostics-storage-and-execution-policies); concrete defaults and enforcement remain to be reviewed and approved before the affected boundary and any untrusted production work. They are not a reason to build an authority prototype merely to choose a client.

## Minimal remaining native acceptance and gate placement

**Accepted handoff: no further broad decision-stage prototype.** Remaining representative native checks move to the **first GTK4 implementation increment, before committing to the rich text/diff component**. The maintainer explicitly approved this revision of A17/A18's outstanding D timing; it does not assert a pass or remove their I/R requirements.

The component checkpoint is one bounded flow: keyboard open file/diff → select a range → draft feedback → return to inspection; verify both directions of F6/Tab escape, restoration and non-stealing focus. With Orca, verify exact selected context, diff side/signs, control names/states, unsaved/error/result announcements without token chatter. At 200% text/UI scaling verify reachable controls, readable content and focus; measure rendered AA contrast and respect reduced motion. Start with accessible native text primitives; a failed rich-control candidate must be simplified or replaced before integration, not waived or trigger a complete toolkit bake-off by default. This is still **unexecuted**.

The implementation driver owns evidence; the maintainer owns target/policy changes. In the first integrated slice (A04/A09/A15/A19), run the nominal one-worker trace, real save acknowledgements, frame/queue limits and slow-client recovery; add the four-worker trace at the concurrent-Objectives increment, before release. Include one **30-minute soak** after warmup, alternating views/streaming; require final quiescent PSS within **10% of the post-warmup quiescent baseline** with caches filled and no continuing upward trend. Retain intermediate windows; passing two endpoints alone is not leak evidence. These are accepted regression targets, not existing observations.

Measurement acceptance: at least **five nominal runs** (60s idle and 5 minutes of load each), **200 input actions per run**, **20 warm launches**, **40 file/diff opens per run**; publish per-run nearest-rank p95 and worst samples, memory/CPU timelines, PID/start identities, workloads and hashes. Repeat the installed core flow at release (A17–A19/A21/A22), with real signed components and full provider/authority obligations intact. If actual presentation cannot be instrumented reliably on the supported stack, mark latency **unverified** and obtain an agreed measurement alternative; never substitute the existing two-frame callback number.

**Decision accepted:** these provisional engineering targets and the explicit I/R evidence handoff resolve #13 planning without claiming full-runtime measurements. The maintainer explicitly approved changing the old expectation of measured full-service budgets before #13 closes. [#14's subsequent resolution](https://github.com/MatiasGigena/LADE/issues/14#issuecomment-5699037043) accepts bounded draft/diagnostics/storage/resource policies and the final handoff, approving #14/#1 planning closure. Production implementation and unexecuted validation remain unauthorized/unverified respectively.
