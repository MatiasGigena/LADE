## Contracts required before each implementation boundary

The workflow's logical reference schema, draft policy and minimal comparison are **proposals**. Before implementing affected production components, specify and review the following in the same canonical workflow/readiness documents or a narrowly necessary linked protocol artifact; do not create a parallel product model.

| Boundary | Contract that must be concrete | Required evidence / owner |
| --- | --- | --- |
| Client ↔ Rust | Workspace/Objective/session IDs, association generations, execution lifetime, request/input/batch/operation IDs; controlling-client authentication; preconditions, version mismatch, action acceptance versus completion; bounded framing, ordered event cursor, snapshot/resync and stale-message errors | #7/#11 derivation; implementation driver drafts example messages and reconnect/error traces, Matias ratifies consequential choices; #13 supplies measured size/buffer bounds |
| Rust ↔ SDK worker | Launch-bound identities, input modes, extension semantic UI/timeout, dispatch acknowledgement, streaming/tool/settled mapping, session replacement and stale execution rejection; stderr drain and backpressure | #6/#7; driver produces deterministic installed-SDK trace suite, not a renamed RPC smoke |
| Permission/protected operation | Requested scope, effective grants and generation, pending/effective revocation, immutable extension approval identity, Git mutation schemas, network gateway binding, safe process recreation | #8; driver produces adversarial bounded fixtures and denial/termination evidence before untrusted execution |
| Inspection/feedback/review | Immutable capture manifest, content identity and range encoding, exact target/candidate identity, stale detection, draft revision/write acknowledgement, batch atomicity, return-for-revision and approval invalidation | #10/#11 + workflow proposals; #13 interaction evidence, #14 policy ratification, then driver documents storage/capture/race cases |
| Persistence/reconciliation | SQLite/session/artifact writer ownership, durable artifact-before-reference protocol, accepted-before-dispatch journal, known/uncertain outcomes, snapshot/event retention, disk-full/corruption handling; no transaction across Git/pi/SQLite asserted | #11; driver produces fault matrix/traces at every cross-store boundary; Matias approves any policy tradeoff |
| Installation/update | Actual prerequisites, pinned component manifest, signing/trust bootstrap, matched-version activation journal, backup/migration/health checks and rollback window | #12 + selected #13 client; driver verifies installed paths and tamper/fault cases, not just source-tree startup |

Minimum error categories to instantiate (names are proposals): unauthorized caller, stale association/execution/context/candidate/target, invalid lifecycle, unsupported content, durability unavailable, version mismatch, permission denied/limit reached, interrupted/unknown outcome, and replay cursor expired. Each needs an actionable presentation and explicit safe retry/query behavior. A request ID alone promises neither idempotent external effects nor exactly-once dispatch. Queries and durable deduplication must prevent naive automatic replay while preserving uncertainty.

No CPU, memory, latency, resource limit, checkpoint lag, framing size or replay-retention number is approved by this task. Required bounds cannot remain unbounded in implementation: #13 must measure workloads and select defensible values with units, environment, methodology and failure behavior.

## Gated sequence of verifiable increments

This is a future work plan, not permission to start production code now. Throwaways inform decisions; do not convert their permissive brokers, mock lifecycle or editor shell into the application.

1. **Interaction decision prototype (D, #13).** Use the approved composition and explicit fixture labeling, including independent inspection and the A02–A06/A17 failure paths. No live worker/Git authority needed to resolve interaction, and no fixture claim of real test success. Exit: recorded developer interaction acceptance and a bounded revision-comparison/draft/reference policy proposal ready for #14.
2. **Boundary feasibility probes (D, #13).** Exercise the selected installed SDK with deterministic fake-provider/tool/session fixtures, separately from prior RPC evidence. In disposable repositories and supported Linux execution contexts, test outside-write/protected-Git denial, forged authority, descendant death, acceptance/dispatch crash windows and restart expiry. No personal repository/profile or host-policy changes without explicit authorization. Exit: scoped artifacts establish feasibility or expose a blocking contract revision; not a universal security guarantee.
3. **Matched client evaluation (D, #13).** Compare the same editor-free interaction and loads; fix prototype-only accessibility confounds before declaring a winner. Record hardware, acceleration, host/component versions, cold/warm methodology, repetitions, workload sizes/concurrency, measurement boundaries and growth. Distinguish fixture UI load from real SDK/service load; separate PSS from cgroup totals and input-to-frame from actual presentation. Exit: toolkit/process choice and approved resource/responsiveness/transport limits, with observed bounds rather than invented targets.
4. **Release decision and protocol handoff (D, #14/#1).** Ratify open policies, map D findings and I/R obligations, instantiate identities/inputs/operations/events/errors/permissions/snapshots/reconciliation sufficiently for the first code boundary. Exit: decision-complete scope, reviewed protocol examples and explicit production authorization. Do not mark the map complete with unresolved blocking decisions.
5. **Small complete production slice (I, only after authorization).** Build fresh along accepted boundaries: one Objective from discussion to isolated agent work, full-file/diff inspection, versioned feedback, frozen revision comparison, observed checks, exact approval and separate integration, plus injected disconnect/crash recovery. Start with a deterministic provider fixture to test plumbing; it is not permission to ship only that provider. Exit: retained end-to-end traces and failure assertions, no duplicate product authority in client or worker.
6. **Expand and harden (I/R).** Concurrent Objectives, full pinned pi/provider/auth/resource/extension semantics, contextual terminal, adversarial containment, load/backpressure and retained-history cases; supported signed installation/update/rollback/uninstall. Exit: all applicable matrix rows exercised on actual installed components, limitations explicit, product exercise compared against baseline. A small slice passing never substitutes for this release boundary.
