## Accepted #14 diagnostics, storage and execution policies

Sequential explicit decisions in the #14 walkthrough ratify these policies. They are not production evidence. Exact numerical defaults and enforcement protocols must be reviewed at the boundaries below; an unspecified or unenforced limit cannot authorize execution.

- **Diagnostics:** local bounded rotating operational logs; no automatic telemetry/crash uploads. Exclude credentials, prompts, source code and tool-output bodies by default. Export previews included data and requires explicit developer action; redaction must be tested and is not infallible. Disable optional upstream telemetry where supported; surface unavoidable traffic before release. Required provider/authentication and explicitly authorized tool traffic remain separate and supported. Manual release checking/download remains #12's contract.
- **Durable retention:** Objective/Agent Session history, accepted inputs, candidates, verification evidence and saved drafts/referenced context are not disposable logs. Keep durable history until explicit deletion. A successfully submitted draft may cease being unsent only through the workflow's durable draft-to-accepted-input association; accepted input and its context remain retained. Cleanup is not history deletion. Never trim pi context or delete history merely to satisfy a performance allocation.
- **Storage pressure:** warn visibly; reclaim only disposable caches/logs and proven-unreferenced temporary artifacts. Block captures/submissions/approvals/integration and other actions whose required durability is unavailable. If required results cannot be recorded, stop affected execution and report interruption/uncertainty, not success. Preserve damaged stores for explicit recovery; no silent reset or overwrite. Preserve last durable drafts and the safe-close loss confirmation. Disk monitoring is not a hard writable-storage quota.
- **Execution resources:** Rust-enforced per-Objective and aggregate CPU, memory, process/thread and writable-storage limits must cover workers and descendants, leaving service/client headroom. The driver proposes concrete defaults, accounting, enforcement and exhaustion tests; the maintainer approves before untrusted production execution. Missing enforcement blocks launch. Throttling/limit failures are visible and do not cause automatic retries, larger limits or bypass of Ask/YOLO authority. Accepted PSS/latency targets remain separate engineering acceptance targets.
